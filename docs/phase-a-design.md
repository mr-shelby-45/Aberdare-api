# Phase A design: Identity

Status: approved by Ian on 2026-10-25. This file is the source of truth for Phase A. Where it disagrees with `docs/architecture.md`, this file wins, and you must update `architecture.md` to match (see section 17). If something here is unclear or missing, stop and ask Ian. Do not guess.

Read `CLAUDE.md` sections 4 to 7 first. The patterns proven in the spike (`docs/spike-results.md`, "Final patterns") are the way to do things. Do not invent new ones.

## 1. Goal and scope

A person can sign up as an owner, add staff, log in, and every request then runs as the right person inside the right business. The phase ends with working, tested login and staff endpoints. Nothing about products, sales or sync.

In scope:
- Owner signup and login (email and password), owner and staff PIN, staff first login, devices and shared tablets.
- Access and refresh tokens, the per-request pipeline (auth, tenant, permissions).
- The non-tenant access path for login lookups.
- Staff and device management endpoints.
- The audit log (moved up from Phase G).
- SMS and email sender interfaces with fake implementations.

Out of scope (do not build): real SMS or email sending, push notifications, subscriptions, social login, two-factor authentication beyond what is below, ownership transfer, account deletion, biometrics (client side), anything in Phases B to H.

## 2. Decisions (all approved)

| Topic | Decision |
|---|---|
| Owner login | Email and password. Email and phone both verified at signup. |
| Staff login | Phone, one-time temporary PIN, SMS code, then their own PIN. |
| PIN | 4 digits. Owners and managers also have a PIN (needed for manager override and shared tablets). |
| Daily login | `device_id` + `device_secret` + PIN. The device secret is a random credential issued at registration. |
| Several businesses per person | Allowed. One owner per business. |
| Hashing | Node's built-in `crypto.scrypt` with a server-side pepper. No argon2, no bcrypt. |
| Tokens | `@nestjs/jwt` for access tokens. Approved as a new dependency. |
| Permissions | Live from the database on every request. Not stored in the token. |
| SMS and email | Interfaces plus fakes in Phase A. Real providers later. |
| Audit log | Built in this phase. |
| Table rename | The people table is `person`. `app_user` means only the database login role. |

## 3. Glossary (use these words exactly)

- **person**: one human, identified by phone, across the whole system. Holds account-level facts: phone, email, password. Belongs to no single business. Not tenant-owned.
- **membership**: a person's role inside one business: role preset, extra permissions, status, PIN. Tenant-owned.
- **tenant**: one business. A tenant table has `business_id` and forced RLS.
- **non-tenant**: data that belongs to no single business, or that must be looked up before the business is known. Reached only through the access path in section 5.
- **`app_user`**: the database login the API and worker connect as. Not owner, no BYPASSRLS.
- **`migrator`**: the database login that owns tables and runs migrations.
- **`identity_owner`**: new, no login, owns the lookup functions in section 5.

## 4. Data model

Every tenant table: `id uuid`, `business_id uuid`, `created_at timestamptz`, RLS enabled and forced with the `shop_only` NULLIF policy, composite foreign keys `(business_id, x_id)`, unique `(business_id, id)`. Grants to `app_user` are explicit. Claude Code proposes the exact Prisma schema and SQL for each group and waits for approval before applying (same routine as the spike). Hand-written SQL goes in its own migration files.

**person** (non-tenant)
- `id`, `phone` (E.164, unique), `phone_verified_at`, `email` (lowercase, unique, nullable), `email_verified_at`, `password_hash` (nullable), `password_changed_at`, `failed_login_count`, `login_locked_until`, `created_at`.
- RLS enabled. `app_user` may SELECT a person only when that person has a membership in the current business. `app_user` has no INSERT, UPDATE or DELETE on `person`; writes go through the identity functions.
- Staff persons have no email or password.

**business** (existing, now with RLS)
- Add `name`, `type` (`RETAIL`, `WHOLESALE`, `WAREHOUSE`). Policy: `id = tenant`, for USING and WITH CHECK. Signup creates the business under a tenant setting equal to its new id (generated by the server before the insert).

**membership** (tenant)
- `person_id`, `display_name` (shown on the "Who is selling?" screen), `role_preset` (`OWNER`, `MANAGER`, `ATTENDANT`), `extra_permissions` (text array), `status` (`INVITED`, `ACTIVE`, `SUSPENDED`, `REMOVED`), `pin_hash`, `pin_set_at`, `pin_failed_count`, `pin_locked_until`, `temp_pin_hash`, `temp_pin_expires_at`, `temp_pin_failed_count`, `created_by_membership_id`.
- Unique `(business_id, person_id)`. Exactly one `OWNER` per business (partial unique index, hand-written SQL).

**device** (tenant)
- `name`, `platform`, `secret_hash`, `is_shared`, `status` (`ACTIVE`, `REVOKED`), `registered_by_membership_id`, `push_token` (nullable, unused until Phase F), `last_seen_at`, `last_sync_at` (nullable).

**device_membership** (tenant): which memberships may sell on a shared device. Unique `(business_id, device_id, membership_id)`.

**refresh_token** (tenant)
- `membership_id`, `device_id`, `family_id`, `token_hash`, `expires_at`, `used_at`, `revoked_at`.

**otp_challenge** (non-tenant, no RLS, holds nothing tenant-related)
- `channel` (`SMS`, `EMAIL`), `target` (phone or email), `purpose` (`SIGNUP`, `STAFF_ACTIVATE`, `PASSWORD_RESET`), `code_hash`, `expires_at`, `attempts`, `verified_at`, `consumed_at`, `created_at`.

**audit_log** (tenant, append-only)
- `actor_membership_id` (nullable), `action`, `target_type`, `target_id`, `metadata` (jsonb, never secrets), `ip`, `occurred_at`. `app_user` has SELECT and INSERT only.

## 5. The non-tenant access path

Problem: login must find a person, device or token before any business is known, but RLS shows nothing without a tenant.

Design:
- New role `identity_owner`: NOLOGIN, owns the functions below, not BYPASSRLS (that needs superuser and would break on managed hosting).
- On each affected table (`person`, `membership`, `device`, `refresh_token`, `business`), an extra policy `FOR ... TO identity_owner USING (true)` (and WITH CHECK where it writes). Remember FORCE RLS applies to table owners too, so this policy is what makes the functions work.
- Grant `identity_owner` the minimum privileges, by column where possible. "Grant columns, not tables."
- The functions are `SECURITY DEFINER`, `SET search_path = pg_catalog, public`, no dynamic SQL, `REVOKE EXECUTE ... FROM PUBLIC`, `GRANT EXECUTE ... TO app_user`. Each takes one exact key and returns only the columns needed, for at most a handful of rows. None can list or search.
- `app_user` itself gets no cross-tenant SELECT on anything.

The functions needed (Claude Code proposes exact names and signatures in A1 for approval):
1. Find person by phone (id, verified flags, whether a password exists; never the hash).
2. Find person by email for login (id, password hash, lock fields). Used only by owner login.
3. Record login failure or success for a person (counters and lock).
4. List a person's active memberships (membership id, business id, business name, role, status).
5. Find invited memberships by phone (membership id, business id, temp PIN hash and expiry, attempts).
6. Find device by id (business id, secret hash, status, shared flag).
7. List members of a shared device (display names and membership ids only).
8. Find refresh token by hash, and mark it used atomically.
9. Upsert person by phone (create invited persons, attach email and password at signup).

The role is created in the Docker init script (and by hand on the real host, like the other roles). A migration that needs it must fail with a clear message if it is missing.

Tests in A1 (must pass before anything is built on it):
- `app_user` cannot SELECT from `membership`, `device`, `refresh_token` or `person` outside a matching tenant, with or without tenant context set to another business.
- Each function with a wrong key returns zero rows. With a right key it returns only its documented columns (assert the exact column list).
- No function can be made to return other tenants' rows (try injection-style inputs, empty strings, NULL).
- `app_user` cannot call anything else as `identity_owner` (`SET ROLE` fails).
- The functions still work after `docker compose down -v` and after `prisma migrate reset`.

## 6. Flows and endpoints

All under `/v1`. Public auth endpoints are marked `@Public()` and do not use the tenant interceptor; after they resolve a business they call `TenantRunner.run` themselves. Every response uses the shared error shape. Never reveal whether a phone or email exists (see section 10).

**Owner signup**
1. `POST /auth/signup/start` `{ phone, email }`: creates SMS and email challenges, sends both codes after commit. Always answers 202 with the same body.
2. `POST /auth/signup/verify` `{ phone, email, phone_code, email_code }`: on success returns a signed `signup_token` (10 minutes, purpose `SIGNUP`, contains the two challenge ids).
3. `POST /auth/signup` `{ signup_token, owner_name, business_name, business_type, password, pin, device: { name, platform } }`: one transaction consumes both challenges, upserts the person (sets verified flags, email, password hash), creates the business, the owner membership (`ACTIVE`, PIN hash) and the device. Returns `{ device_id, device_secret, access_token, refresh_token, membership }`. The device secret is shown only here. If the phone or email already belongs to a person with a password, return `ACCOUNT_EXISTS` (safe to reveal here because both codes were proven).

**Owner login on a new phone or after reinstall**
- `POST /auth/login` `{ email, password, device: { name, platform }, membership_id? }`.
  - Unknown email: still run a full dummy hash, return `INVALID_CREDENTIALS`.
  - Person has several active memberships and no `membership_id`: return 200 `{ requires_selection: true, memberships: [...], selection_token }` (signed, 5 minutes). Client calls again with `selection_token` and `membership_id`.
  - Success: creates a device, returns the same bundle as signup (device secret shown once).

**Password reset**
- `POST /auth/password/forgot` `{ email }`: always 202. If the email belongs to a verified person, send a code (10 minutes).
- `POST /auth/password/reset` `{ email, code, new_password }`: sets the password, revokes all refresh tokens of that person in every business.

**Staff first login**
1. Owner creates staff (section 8). The app shows the temporary PIN once.
2. `POST /auth/first-login` `{ phone, temp_pin }`: checks the temp PIN against the person's invited memberships (function 5). On a match, creates an SMS challenge, sends the code, returns a signed `setup_token` (10 minutes, contains membership id and challenge id). Bad PIN, unknown phone, expired PIN all return the same `INVALID_CREDENTIALS`. If two invited memberships match the same temp PIN, return `AMBIGUOUS_INVITE` and tell the owner to reset one.
3. `POST /auth/staff/activate` `{ setup_token, code, new_pin, device: { name, platform } }`: verifies the code, sets the PIN, marks the phone verified, clears the temp PIN, sets the membership `ACTIVE`, creates the device. Returns the same bundle.

**Daily PIN login**
- `POST /auth/pin` `{ device_id, device_secret, pin, membership_id? }`. Server finds the device (function 6), checks the secret (constant time), picks the membership (the device's only one, or `membership_id` on a shared device, which must be in `device_membership`), checks the PIN, status and locks, and returns tokens (no new device secret).

**Shared tablet list**
- `GET /auth/device-members` with `device_id` and `device_secret` in headers. Returns display names and membership ids for that device only. Returns an empty list with the same status for a bad credential, so it cannot be probed.

**Refresh and logout**
- `POST /auth/refresh` `{ refresh_token }`: rotates. Reusing an already-used token revokes the whole family. The client then falls back to PIN login, which is easy, so the strict rule is acceptable.
- `POST /auth/logout` (authenticated): revokes the current refresh token. The device stays registered.

**Who am I**
- `GET /me` (authenticated): membership, effective permissions, business.

## 7. Tokens and secrets

- Access token: JWT, 15 minutes, claims only `sub` (person id), `mid` (membership id), `bid` (business id), `did` (device id). No permissions, no names.
- Refresh token: 32 random bytes (`crypto.randomBytes`), base64url. Store only the SHA-256 hash. Lifetime 30 days, rotated on use.
- Device secret: 32 random bytes, base64url. Store only the SHA-256 hash (high entropy, so a fast hash is fine). Compare with `crypto.timingSafeEqual` on equal-length buffers.
- OTP and temp PIN digits: `crypto.randomInt`. Never `Math.random`.
- OTP, email code, temp PIN and PIN storage: HMAC-SHA256 with the server pepper for codes; scrypt for PINs and passwords.
- scrypt: self-describing stored format (`scrypt$N$r$p$salt$hash`) so parameters can be raised later. Start from OWASP's current scrypt guidance (verify it before choosing; for example N=2^15, r=8, p=3), a 16-byte random salt, a 64-byte output, and set `maxmem` high enough that Node does not reject the call. Pre-hash with the pepper (HMAC) before scrypt. Measure the cost; aim for roughly 50 to 150 ms per hash on the dev machine and tell Ian the number.
- Secrets (JWT secret, pepper) come from validated environment variables. The app refuses to start if they are missing or shorter than 32 characters. `.env.example` has fakes only.

## 8. Per-request pipeline (read twice, easy to get wrong)

Nest runs guards before interceptors. A guard cannot use the tenant transaction, so database checks must not live in a guard.

1. Rate limit (already built).
2. `AuthGuard`: verifies the access token only (signature, expiry). Puts `{ personId, membershipId, businessId, deviceId }` in the request context. Skips routes marked `@Public()`.
3. `TenantInterceptor`: calls `TenantRunner.run(businessId, ...)` around the handler. Inside the transaction, first query: load the membership and device by id. Refuse with `MEMBERSHIP_INACTIVE` or `DEVICE_REVOKED` unless both are `ACTIVE`. Compute effective permissions (section 9). Read the `@RequirePermission(...)` metadata with `Reflector` and refuse with `PERMISSION_DENIED` if missing.
4. Handler (controller, service, repository) runs in the same transaction.

`business_id` comes only from the token. A `business_id` in any body, query or header is rejected by validation (the spike already forbids unknown properties).

## 9. Permissions

Permissions are string constants in one file (`common/auth/permissions.ts`), with the role presets defined next to them. Effective permissions = preset plus `extra_permissions`, computed on every request.

| Permission | Attendant | Manager | Owner |
|---|---|---|---|
| sales.create, payments.confirm, stock.view, orders.manage | yes | yes | yes |
| products.edit, stock.receive, stock.adjust, stock.convert, stock.count | no | yes | yes |
| sales.void, payments.approve, reports.view | no | yes | yes |
| costs.view, staff.manage, devices.manage, subscription.manage, shopkey.manage | no | no | yes |

- `stock.convert` can never be an extra permission on an attendant. Reject it at write time and ignore it at read time.
- The owner cannot be suspended, removed or demoted. There is one owner per business.
- Only people with `staff.manage` may call the staff endpoints; only `devices.manage` the device endpoints.

## 10. Security limits and rules

| Item | Rule |
|---|---|
| SMS code | 6 digits, expires 5 minutes, 5 attempts, 60 s between sends, 5 sends per target per hour, 10 per day |
| Email code | 6 digits, expires 10 minutes, same attempt and send limits |
| Temp PIN | 6 digits, single use, expires in 3 days, 5 wrong tries kills it |
| PIN | 4 digits. 5 wrong tries lock the membership for 15 minutes. 10 failures in a row need an owner reset (staff) or a password login (owner) |
| Password | 10 to 128 characters, must not equal the email, phone or the email's local part. Common-password list is a later improvement |
| Password login | 5 wrong tries lock that person for 15 minutes. Per-IP rate limit on every public auth route |
| Enumeration | Same response and same work for known and unknown phones and emails. Always run a dummy hash for an unknown email |
| Logging | Never log codes, PINs, passwords, tokens, device secrets, or full phone numbers. Fake senders must not log codes |
| Audit | These events go to `audit_log`: signup, device registered or revoked, shared flag changed, staff created, updated, suspended, reactivated, removed, PIN reset, password changed or reset, PIN lockout, refresh token reuse detected |

## 11. Staff and device endpoints

All require a token and the stated permission.

- `POST /staff` (`staff.manage`): `{ phone, display_name, role_preset, extra_permissions? }` (preset `MANAGER` or `ATTENDANT` only). Upserts the person, creates the membership `INVITED` with a generated temp PIN, returns `{ membership_id, temp_pin, temp_pin_expires_at }`. The temp PIN is shown once and stored hashed.
- `GET /staff`, `PATCH /staff/:id` (display name, preset, extra permissions), `POST /staff/:id/reset-pin` (new temp PIN, membership back to `INVITED`, revoke its tokens and device links), `POST /staff/:id/suspend` (revoke refresh tokens), `POST /staff/:id/reactivate`, `DELETE /staff/:id` (status `REMOVED`, never a hard delete).
- `GET /devices`, `PATCH /devices/:id` (name, `is_shared`), `DELETE /devices/:id` (revoke, revoke its tokens), `POST /devices/:id/members` and `DELETE /devices/:id/members/:membershipId` (`devices.manage`).
- `GET /me`.

## 12. Error codes

`INVALID_CREDENTIALS`, `ACCOUNT_LOCKED` (with retry time), `OTP_INVALID`, `OTP_EXPIRED`, `OTP_RATE_LIMITED`, `ACCOUNT_EXISTS`, `AMBIGUOUS_INVITE`, `TOKEN_EXPIRED`, `TOKEN_INVALID`, `MEMBERSHIP_INACTIVE`, `DEVICE_REVOKED`, `PERMISSION_DENIED`, `SELECTION_REQUIRED`, `VALIDATION_FAILED`. All use the shared error shape. Messages are safe for users and never say which of phone, email or PIN was wrong.

## 13. Integrations

- `integrations/sms/SmsSender` and `integrations/email/EmailSender`: one method each (`send(target, message)`), nothing else. Sending happens after the database commit, never inside a transaction.
- Fakes: an in-memory outbox that tests read. In non-production environments with `AUTH_DEV_FIXED_CODES=true`, every code is `123456` for numbers or emails on an explicit dev allowlist. The app must refuse to start in production if this flag is true.
- Real implementations (Africa's Talking, an email provider) are not built in this phase. Provider and sending domain are decided before launch.

## 14. Audit log

A small `AuditService.record(action, target, metadata)` used by services (not repositories calling each other). It writes in the same transaction as the change it records. Never put secrets or full phone numbers in `metadata`.

## 16. Mistakes AI tends to make here (do not)

- Putting permissions or names in the JWT.
- Doing database checks (membership status, permissions) in a Nest guard. Guards run before the tenant transaction exists. Use the interceptor as in section 8.
- Calling SMS or email inside a database transaction.
- Returning different errors, shapes or timings for known and unknown phones or emails.
- Using `Math.random`, `===` for secrets, or storing any code, token or secret in plain text.
- Logging a code "just for development", even in the fake sender.
- Adding Passport, bcrypt, argon2, a session library, or any package not approved. The only new package approved is `@nestjs/jwt`.
- Building one giant `User` table or one `AuthService` that does everything. Keep modules: `auth`, `staff`, `devices`, `audit`, plus `integrations/`.
- Letting `app_user` read `person`, `membership`, `device` or `refresh_token` across tenants "to keep it simple".
- Using dynamic SQL or string concatenation inside the `SECURITY DEFINER` functions, or forgetting `SET search_path` and the `REVOKE ... FROM PUBLIC`.
- Treating the PIN as the staff's whole identity. The device secret and the membership are what identify them.
- Changing a fixed rule to make a test pass. Report and ask.

## 19. Test plan

All of these are automated, run against the real Docker database, and must pass before a step is called done. Same rules as the spike: never weaken a test to make it pass, run concurrency tests repeatedly, and report failures honestly.

Time rule: lockouts, expiries and rate windows must use an injectable clock (a tiny `Clock` provider in `common/time/`), never real sleeps and never `new Date()` scattered in services. Tests move the clock forward instead of waiting 15 minutes.

**A1: non-tenant path and business RLS**
1. `app_user` cannot read `membership`, `device`, `refresh_token` or `person` rows of another business, with a tenant set to someone else and with no tenant set.
2. Each identity function returns zero rows for a wrong key and exactly its documented columns for a right key (assert the column list).
3. Inputs like an empty string, NULL, a very long string and SQL-looking text return nothing and never error in a way that leaks.
4. `app_user` cannot `SET ROLE identity_owner`, cannot create or alter functions, and cannot call functions that were not granted to it.
5. `business` RLS: business A cannot see or update business B. An insert whose id equals the tenant works. An insert with a different id is rejected.
6. `person` is readable only through a membership of the current business, and `app_user` cannot insert, update or delete it directly.
7. After `docker compose down -v` and after `prisma migrate reset`, all of the above still pass (reset check done by hand with Ian's consent, as in the spike).

**A2: codes and signup**
1. Codes are stored hashed. No plaintext code appears in any table or log.
2. Expired codes, wrong codes, a sixth attempt, and a reused code are all refused. The wrong-attempt counter is atomic under concurrent guesses (20 parallel wrong guesses count exactly 20).
3. Resend cooldown, hourly cap and daily cap work. Per-IP limits work.
4. `signup/start` returns the same status and body for a new, known and unverified phone or email.
5. `signup_token` is refused when expired, tampered, replayed, used for another purpose, or paired with different challenge ids.
6. Signup is atomic: a forced failure after the business insert leaves no person, business, membership, device or consumed challenge behind.
7. `ACCOUNT_EXISTS` appears only after both codes are proven.
8. A person created earlier as a staff invite (unverified phone) can sign up as an owner after proving the phone, and keeps their existing memberships.
9. The app refuses to start in production with `AUTH_DEV_FIXED_CODES=true`, and refuses to start when the JWT secret or pepper is missing or too short.

**A3: login, tokens, pipeline**
1. Password login works. Wrong password and unknown email return the same status, body and error code. Unknown-email work time is within a loose factor of known-email time (sanity check, not a strict timing proof).
2. Five wrong passwords lock the person for 15 minutes (clock moved). A correct password during lockout is still refused. After the window it works.
3. PIN login works. A wrong device secret, a revoked device, a membership that is not on the shared device, and a wrong PIN are all refused. Five wrong PINs lock for 15 minutes. Ten in a row need a reset.
4. A valid access token for a suspended or removed membership, or a revoked device, is refused on the very next request.
5. A token for business A cannot read or write business B's data, tested with seeded data in both and with requests that include a `business_id` in the body, query and header (all rejected or ignored).
6. `@RequirePermission` is enforced inside the tenant transaction. An attendant is refused a manager-only route, an extra permission grants access, and changing a permission takes effect on the next request.
7. Refresh rotates. The old token fails. Reusing a used token revokes the whole family. Two concurrent refreshes with the same token: exactly one succeeds (20 runs in a row).
8. Logout revokes the current refresh token. An expired access token returns `TOKEN_EXPIRED`.
9. A person with several memberships gets `requires_selection`, and a bad or expired `selection_token` is refused.

**A4: staff and devices**
1. Staff creation returns the temp PIN once. It is stored hashed. `GET /staff` never returns any hash or secret.
2. First login works with the right phone and temp PIN. Wrong PIN, unknown phone and expired PIN all give the same response. The fifth wrong try kills the temp PIN. Reuse after activation fails.
3. Two invited memberships with the same temp PIN give `AMBIGUOUS_INVITE`.
4. Activation needs the correct SMS code and sets the phone verified, the PIN, status `ACTIVE`, and a device.
5. `reset-pin` and `suspend` revoke tokens and, for reset, require a fresh first login. `reactivate` restores access.
6. The owner cannot be suspended, removed or demoted. `stock.convert` cannot be added to an attendant (rejected on write and ignored on read).
7. An attendant without `staff.manage` or `devices.manage` gets `PERMISSION_DENIED`.
8. The shared-device list returns display names and membership ids only, only for that device, and an empty list for a bad credential.
9. Staff, device and token queries from business A never return business B's rows.

**A5: audit and hardening**
1. Each event in section 10 writes an audit row in the same transaction. A rolled-back action leaves no audit row.
2. `audit_log` is append-only for `app_user` (UPDATE and DELETE fail).
3. For every credential type (password, PIN, temp PIN, SMS code, email code, access token, refresh token, device secret, signup and setup tokens), a test sends it through success, failure and 500 paths and proves it never appears in any log line.
4. Enumeration tests: status, body shape and error codes are identical for known and unknown phones and emails on every public route.
5. The full suite passes ten runs in a row with no flaky test.

**Proof the tests catch mistakes (as in the spike).** Apply each of these temporarily, show the named test failing, then revert:
1. Skip the membership status check in the interceptor: A3 test 4 must fail.
2. Make refresh rotation read-then-write instead of one atomic statement: A3 test 7 must fail.
3. Remove the single-use check on a code: A2 test 2 must fail.
4. Return a different error for an unknown email: A3 test 1 and A5 test 4 must fail.
5. Stop redacting the device secret in logs: A5 test 3 must fail.
6. Remove `REVOKE EXECUTE ... FROM PUBLIC` on one identity function: the A1 grants test must fail.
